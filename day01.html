DAY 01 · 2026-11-18 · 120 MINUTES

定位并优化一个慢 GEMM

真实工程任务：建立基线 → 采集时间线 → 分析单 Kernel → 对照优化 → 提交性能归因。

← 返回 43 天课表

本日目标

  • 使用 Nsight Systems 区分 Host、Memcpy、Kernel 和同步开销。
  • 使用 Nsight Compute 读取 Launch、Occupancy、Memory、Warp Stall 证据。
  • 比较 naive GEMM 与 tiled GEMM，解释 Shared Memory 数据复用与资源代价。
  • 验证 pinned memory 是否真的带来 Copy/Compute overlap。

实验环境

使用公开实验仓库 csl-iisc/gpu-profiling-tutorial。代码与原始 Profile 结果请保存在你的私有学习仓库，不要上传到公开课程站点。

git clone https://github.com/csl-iisc/gpu-profiling-tutorial.git
cd gpu-profiling-tutorial
make

先阅读仓库 README / Makefile，确认编译产物、依赖和参数。GPU 资源不足时降低矩阵规模。

任务 A · 建立正确性和性能基线（20 分钟）

./naive_gemm 1024
./naive_gemm 2048

记录 GPU 型号、驱动、CUDA、编译选项、矩阵维度、正确性、重复运行的中位数。预热和首次初始化单独记录，不要只跑一次。

任务 B · Nsight Systems 时间线（20 分钟）

nsys profile --trace=cuda -o gemm_naive ./naive_gemm 2048
nsys stats gemm_naive.nsys-rep
  1. H2D、Kernel、D2H 分别占多少时间？
  2. CPU 提交是否有空洞？是否存在同步等待？
  3. Kernel 占端到端时间多少？如果只有 15%，优先优化 Kernel 是否合理？

任务 C · Nsight Compute 单 Kernel 分析（25 分钟）

ncu --set full -o gemm_naive_ncu ./naive_gemm 2048

检查 Launch Statistics、Occupancy、Compute/Memory Throughput、Warp Stall、Memory Workload。提出一个主要瓶颈假设，至少列出两项支持证据和一项反证/待验证项。不要凭单一 Stall 百分比直接下结论。

任务 D · naive 与 tiled 对照（25 分钟）

./tiled_gemm 2048
ncu --set full -o gemm_tiled_ncu ./tiled_gemm 2048
nsys profile --trace=cuda -o gemm_tiled ./tiled_gemm 2048

比较相同规模、精度和正确性要求下的耗时；分析 Shared Memory 复用、DRAM/L2 流量、寄存器、Occupancy、同步成本。若 tiled 更慢，也要解释原因，不得强行写成优化成功。

任务 E · Pinned Memory 与异步重叠（15 分钟）

比较普通 Host Memory 和 pinned Host Memory 版本。Pinned Memory 本身不保证 overlap。检查异步拷贝、Streams、依赖关系和 Copy Engine，并用 Nsight Systems 时间线证明是否真实重叠。

资源模型推导（10 分钟）

简化假设：每 SM 65536 个 32-bit registers、2048 threads、64 warps、16 blocks；256 threads/block；64 registers/thread；不使用 Shared Memory。

  • 每 Block registers = 256 × 64 = 16384。
  • Register 限制允许 4 Blocks；线程/warp 限制各允许 8 Blocks。
  • 简化模型取最小值 4 Blocks，活跃 Warp = 32，理论 Occupancy = 50%。

将每线程寄存器改为 32，重新计算理论 Occupancy，并解释为什么实际性能不保证提升：分配粒度、spill、指令数、访存量和真实架构限制。
